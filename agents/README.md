# Data Center — AI Agent Simulation

> **Status: DRAFT (Phase 1 foundation).** This system scaffolds an "AI agent
> team" that uses the live Data Center app the way real sysadmins would —
> running cases, querying the AI Search/Diagnose endpoints, getting
> happy/irritated/angry, and filing reports and suggestions back to a
> dashboard. Agents 1-4 have full behavioral state machines. Agents 5-11 are
> placeholder stubs for Phase 2 — **the agent specification document is not
> final**, so prioritize structure and interfaces over completeness when
> extending this.

---

## Overview

Each simulated agent is a small state machine (mood, irritation, optional
panic) that:

1. Receives a batch of IT support **cases** (generated by `case-generator.js`).
2. Decides whether to solve a case independently or query the live app
   (`interactWithApp()` → `data-center-api` Worker's `/api/chat`).
3. Asks **Gemini 2.0 Flash** to role-play the decision/response in-character,
   using its `system_prompt_additions` + `behavioral_rules` from
   `config/agents-config.json`.
4. Updates mood/irritation/panic based on a (placeholder) response-quality
   heuristic, and may transition to `HAPPY`, `IRRITATED`, `ANGRY`, or (Agent 4
   only) `PANIC`.
5. Files **reports** (incident/status/weekly) and **suggestions** to D1.
6. Persists its full state to a per-agent **Durable Object** between runs.

A **scheduler Worker** drives this on a cron: an hourly "work day" cycle and
a daily "work week" reset cycle (time-scaled per `config/simulation-config.json`).
An **admin dashboard** (in-app 🔐 Admin tab, plus a standalone
`dashboard/admin-panel.html`) lets a human watch agent status, the live
session feed, reports/suggestions, and control the simulation.

│   ├── agent-1-perfectionist.js # Phase 1
│   ├── agent-2-productive.js    # Phase 1
│   ├── agent-3-standard.js      # Phase 1
│   ├── agent-4-trainee.js       # Phase 1
│   └── agent-stub.js            # Phase 2 placeholder (agents 5-11)
├── dashboard/
│   ├── admin-panel.html         # standalone admin dashboard
│   └── dashboard.js             # shared dashboard logic (DCAdmin)
├── reports/templates/           # markdown templates: incident, status, weekly
├── database/
│   ├── schema.sql                # D1 schema (agents, agent_sessions, cases, interactions, reports, suggestions, weekly_analytics)
│   └── seed-cases.sql            # seed agents + starter case batch

├── README.md                      # this file
└── AGENTS.md                      # agent specification reference (summary)

The in-app **Admin tab** (`index.html`, `dataset.moduleId = 'admin'`) is a
read-only client for `agent-runner.js`'s HTTP API — it does not duplicate any
simulation logic. The standalone `dashboard/admin-panel.html` is the same
idea as a non-bundled page, useful for testing the API independently of
GitHub Pages.

## Agent tiers

### Phase 1 — full behavioral state machines

| # | Name | Role | Clearance | Key trait |
|---|------|------|-----------|-----------|
| 1 | The Perfectionist | QA Lead | standard | Never gets angry; "educates the algorithm"; only calms down once a case is solved *and* documented. |
| 2 | The Productive | Senior IT Operator | standard | Irritation stack (max 3) → `ANGRY` + incident report + cooldown; 30% overtime days; bonus days when +30% over quota. |
| 3 | The Standard Agent | IT Generalist | standard | `model_usage_rate = mood / 100`, recalculated every session; files balanced status reports. |
| 4 | The Trainee | Junior IT Support | standard | Tracks `panicLevel` (0-100); at ≥80 fires `TRAINEE_PANIC`, escalating to a senior agent for a joint session and (Phase 2) an auto-generated guide. |

### Phase 2 — stubs only (`agent-stub.js`, inherits `AgentBase` defaults)

| # | Name | Role | Clearance |
|---|------|------|-----------|
| 5 | The Specialist | Network & Security Specialist | standard |
| 6 | The Senior Sysadmin | Senior Systems Administrator | sudo |
| 7 | The Security Auditor | Security Auditor | sudo |
| 8 | The DevOps Engineer | DevOps / Automation Engineer | sudo |
| 9 | The Helpdesk Coordinator | Helpdesk Coordinator | standard |
| 10 | The IT Director | IT Director | root |
| 11 | The CTO | Chief Technology Officer | root |

`config/simulation-config.json` controls which agents actually run
(`SIMULATION.active_agents` / `SIMULATION.stub_agents`) and the
root/sudo/standard permission tiers used for `fileSuggestion()` routing.

## Setup (manual — not automated by this commit)

These steps provision the Cloudflare resources the Workers expect. None of
this is required for the static site itself to keep working.

1. **Google AI Studio API key** — create a Gemini API key and store it as a
   Worker secret: `wrangler secret put GEMINI_API_KEY` (for both
   `agent-runner` and `scheduler` Workers, or a shared Worker if you combine
   them).

2. **Cloudflare D1** — create a database and apply the schema:
   ```bash
   wrangler d1 create data-center-agents
   wrangler d1 execute data-center-agents --file=agents/database/schema.sql
   wrangler d1 execute data-center-agents --file=agents/database/seed-cases.sql
   ```
   Bind it as `DB` in both Workers' `wrangler.toml`.

3. **Durable Objects** — bind `AGENT_STATE` to `state-manager.js`'s
   `AgentStateDO` class in `agent-runner.js`'s `wrangler.toml`, and add the
   required migration block (`new_classes = ["AgentStateDO"]`).

4. **KV namespace** — create `SIM_KV` and bind it to both `agent-runner` and
   `scheduler` Workers. This holds the live `inspection_mode` / `paused` /
   `phase` overrides written by the Admin tab's Simulation Controls panel.

5. **Cron Triggers** — in `scheduler.js`'s `wrangler.toml`:
   ```toml
   [triggers]
   crons = ["0 */1 * * *", "0 0 * * *"]
   ```
   (hourly work-day cycle, daily work-week reset — see
   `config/simulation-config.json`'s `TIME_SCALE`).

6. **`ADMIN_TOKEN` secret** — pick a strong random token and set it on
   **both** Workers:
   ```bash
   wrangler secret put ADMIN_TOKEN   # agent-runner
   wrangler secret put ADMIN_TOKEN   # scheduler
   ```
   This token is **never** embedded in `index.html` or `dashboard.js` — the
   admin types it into the dashboard once, it's stored in `localStorage`,
   and sent as the `X-Admin-Token` header on every `/api/agents/*` and
   `/run/day` / `/run/week` request. The Worker validates it server-side.
   See CLAUDE.md's credential rules.

7. **`GITHUB_TOKEN` secret (optional, Phase 2)** — only needed if/when
   `scheduler.js`'s `commitGuideToArchive()` should actually commit
   auto-generated trainee guides to `data-center-archive/guides/`. Without
   it, guide commits silently no-op.

8. **Test the admin dashboard** — open the in-app 🔐 Admin tab (or
   `agents/dashboard/admin-panel.html`), enter the `ADMIN_TOKEN` value, and
   confirm the agent status grid loads from `agent-runner`'s
   `/api/agents/status`.

### Environment variables / bindings summary

| Name | Used by | Type | Purpose |
|------|---------|------|---------|
| `GEMINI_API_KEY` | agent-runner, scheduler | secret | Gemini 2.0 Flash API key |
| `ADMIN_TOKEN` | agent-runner, scheduler | secret | Validates `X-Admin-Token` on admin/control endpoints |
| `GITHUB_TOKEN` | scheduler | secret (optional) | Commits Phase 2 trainee guides to `data-center-archive` |
| `DB` | agent-runner, scheduler | D1 binding | `agents`, `agent_sessions`, `cases`, `interactions`, `reports`, `suggestions`, `weekly_analytics` |
| `AGENT_STATE` | agent-runner, scheduler | Durable Object binding | `AgentStateDO` — per-agent persisted state |
| `SIM_KV` | agent-runner, scheduler | KV binding | Live simulation overrides (`inspection_mode`, `paused`, `phase`) |
| `APP_API_BASE` / `APP_ORIGIN` | agents (via env) | plain vars | Where `interactWithApp()` sends `/api/chat` requests |

### CI variables/secrets for `.github/workflows/agent-*.yml`

| Name | Type | Purpose |
|------|------|---------|
| `vars.AGENTS_API_BASE` | repo variable | Base URL of the deployed `agent-runner` Worker |
| `vars.AGENTS_SCHEDULER_BASE` | repo variable | Base URL of the deployed `scheduler` Worker |
| `secrets.ADMIN_TOKEN` | repo secret | Same value as the Worker's `ADMIN_TOKEN` secret |

`agent-cases.yml` (weekly case batch) needs none of these — it only runs
`case-generator.js` locally and commits the result. `agent-reports.yml`
(weekly report) no-ops with a step-summary notice until all three are set.

## Local development

```bash
# Validate config/data as usual
node .github/scripts/validate-json.js
node .github/scripts/health-check.js

# Generate a one-off case batch (writes agents/database/cases-<year>-w<week>.json)
node .github/scripts/generate-agent-cases.mjs

# Run a Worker locally (from agents/workers/, after wrangler.toml is added)
wrangler dev agent-runner.js
wrangler dev scheduler.js
```

There is intentionally **no `wrangler.toml` checked in yet** — bindings
(D1 database ID, KV namespace ID, Durable Object migration) are
environment-specific and should be created during the manual setup above,
then committed once finalized.

## Known gaps / Phase 2 TODO

- `evaluateResponseQuality()` and `getDbContext()` in `agent-base.js` are
  placeholders (length-based heuristic / empty string).
- Agents 5-11 have no behavioral state machines — `agent-stub.js` just
  inherits `AgentBase` defaults.
- `commitGuideToArchive()` in `scheduler.js` no-ops without `GITHUB_TOKEN`.
- `weekly_analytics` columns `irritation_count`, `happy_count`,
  `overtime_days`, `suggestions_filed` are not yet populated by
  `runWeeklyResetCycle()` — `agent-reports.yml`'s generated summary shows
  `—` for these until a future iteration computes them from
  `agent_sessions`/`interactions`.
- Acknowledging reports from the Admin tab (`adminAcknowledge()` in
  `index.html`) is currently client-side only — a
  `POST /api/agents/reports/:id/ack` endpoint is needed to persist it.
